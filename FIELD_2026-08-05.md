## 2. What was fixed and confirmed in the field

### 2.1 The reported regression: YouTube's `Auto-dubbed` badge

Root cause of "Shorts stopped scrobbling". YouTube began rendering an **`Auto-dubbed`** badge in the
Shorts footer as a bare `android.view.View` — no resource id, no button class, no control
vocabulary — so it survived every rule in `isTitleLike` and stood as a *second* title candidate.
`singleOrNull()` returned null, identity refused silently, the Short finalized at `measured 0s` and
was skipped below threshold. **No app install is needed for this to appear**, which is why "nothing
was installed" was true and misleading at once.

Fixed by `BADGE_LABELS` (exact-label match). **Confirmed in the field**: measurement heartbeat
`seekbar advanced` went from 0–2/hour to **258/hour**, and ten Shorts reached the chain including
`@enefectoescine17`, the auto-dubbed case that had been refusing.

### 2.2 Accessibility drops were completely silent

`dumpsys accessibility` listed both services under `crashed services`; Android had removed
`UrlWatcherService` from `enabled_accessibility_services` without the owner touching anything.
Browser evidence was dead for most of the day and **nothing anywhere reported it**.

§9.3 closed on the owner's sign-off: `UrlWatcherService.isEnabled` now also requires
`accessibility_enabled == 1`. Reporting only — no capture logic changed, so Chrome/Brave behave
identically whenever the service is live. Added `AccessibilityGrantHealth`
(`LIVE`/`NEVER_GRANTED`/`SETTLING`/`DROPPED`), a one-way "was once live" flag in `Settings`, distinct
Settings copy, and one `[health]` line per transition.

### 2.3 The device caught a defect in 2.2 before it shipped

Right after `adb install -r`, `accessibility_enabled` reads **0** while both services are still
named in the list, settling to 1 seconds later with both reconnecting (§2.3 of the phase doc). The
first cut would have shouted "this crashed" on **every install**. Hence `SETTLING` and a 15-second
dwell.

## 3. What is shipped and WRONG — fix these first

Both are cosmetic (no scrobble decision is affected) but both are actively misleading.

1. **`SessionSnapshot.foregroundProgressLost` is far too broad.** It is wired to
   `frozenForMissingProof`, which is true whenever a Short *ends* — including scrolling away. The
   result is that "(progress surface lost …)" is appended to essentially **every** Short finalize
   line, including ordinary ones. The marker must instead be driven by the specific parser outcome
   `times.size == 0` while `timeBars.size == 1` (see §4.2), not by generic proof loss.
2. **The new refusal reason is unreachable on the common path.** It was added to
   `ScrobbleRules.decide()`, but `ScrobbleRules.prefilter()` — "the cheap rejection, before any
   network call" — short-circuits first and still emits `played N%, below 60% threshold`. The same
   handling has to exist in `prefilter`, or the marker has to be consulted before it.

## 4. Measurements — do not re-derive these

### 4.1 Picture-in-picture has no progress source (both directions)

Measured with a Short live in PiP, window confirmed `mWindowingMode=pinned` /
`mLastReportedPictureInPictureMode=true`, bounds `[435,889][690,1342]` versus fullscreen
`[0,45][720,1420]`.

| source | in PiP |
| --- | --- |
| MediaSession | `active=true`, 3 controllers — but `state=0` (`STATE_NONE`), `position=0` |
| accessibility tree | keeps `reel_watch_fragment_root`, `reel_watch_player`, `reel_time_bar` — **no `SeekBar` child**, no time text anywhere in the window |

### 4.2 The PiP signature, exactly

`timeBars.size == 1 && times.size == 0` → `expected exactly one readable Shorts seekbar time; found
0`. Confirmed: 82 of these and **zero** container failures during PiP. This is the signal item 3.1
should use.

### 4.3 Disproven hypotheses (do not re-run)

- **"The Shorts seekbar auto-hides when untouched."** Wrong. Untouched for 20+ seconds the `SeekBar`
  persisted and advanced: `3s → 9s → 17s → 24s → 30s`.
- **"PiP poisons the seekbar even after returning to fullscreen."** Wrong. It is restored within
  ~5 seconds of returning and survives a swipe to the next Short.

### 4.4 Audio playback DOES distinguish playing from paused in PiP

This is what makes a PiP fallback conceivable at all.

```
playing in PiP        : AudioPlaybackConfiguration ... u/pid:10201/... state:started  usage=USAGE_MEDIA
paused by hand in PiP : AudioPlaybackConfiguration ... u/pid:10201/... state:paused
MediaSession, both    : state=0 (STATE_NONE), position=0
```

An earlier test using `KEYCODE_MEDIA_PAUSE` was **inconclusive** — YouTube ignores the media keys in
PiP, so the state did not change. Only a hand-pause proved it. Do not repeat the keyevent version.

**Unverified risk before building on this:** the above is what `dumpsys` shows, i.e. what the
*system* knows. `AudioPlaybackConfiguration.getPlayerState()` and `getClientUid()` are hidden/system
APIs and Android redacts fields for other apps' players. The public path is
`AudioManager.getActivePlaybackConfigurations()` / `registerAudioPlaybackCallback`, where paused
players are *expected* to drop out of the list — but **whether a remaining config can be attributed
to YouTube from a normal app must be verified in code**. If attribution fails, the idea dies there.
That spike comes before any implementation.

## 5. Open bugs, in priority order

### 5.1 The accessibility event stream goes silent — TOP PRIORITY

Between **17:19:40 and 17:21:07 the log contains two lines**, at 17:20:10 and 17:20:40, exactly 30s
apart. That is the idle poll and nothing else: the observer received **no YouTube accessibility
events for 87 seconds** while a Short was playing. In the same session the Short titled
`💯💯💯🔥😎` **never appears in the log at all** — never observed, never finalized.

This is the same shape as the 13h outage and it explains the two regular-mode Shorts that did not
scrobble far better than any seekbar theory. It costs more listens than PiP ever will, and it is
very likely the reason ~half of the day's watch history never reached the app (§4.5).

At hand-off the service looks healthy — `crashed services: {}` empty, both grants on, standby bucket
10 — so it is **intermittent**, and cannot be reproduced on demand.

**Recommended first move:** instrument it. Log when the Shorts observer has received no YouTube
event for N seconds while YouTube is the foreground package, so the next occurrence names itself
instead of being inferred from gaps. Only then hunt the cause (candidates: service crash/rebind,
Samsung background management, window-state transitions).

### 5.2 PiP measurement fallback

Design settled, spike outstanding (§4.4). Accumulate wall-clock only while YouTube's audio is
`started`; duration is already known from the last foreground proof and confirmable from watch
history; cap at `min(elapsed, duration)` so loops cannot over-count; assume 1× speed and document it.
Must be **opt-in behind its own switch, logged as inferred rather than measured, and never used when
foreground proof is available**.

Note the UI has always stated PiP is not counted ("Foreground Shorts only; PiP/background time is
not counted"), so this is a feature, not a regression.

### 5.3 Still open from §9

§9.1 (duplicate-upload field test), §9.2 (can the native search fallbacks go), §9.4 (translated-title
gap outside Shorts), §9.5 (consolidate the title comparison — this session added a second instance of
the smell and then split it).

### The signing trap — read before installing

The laptop generated its **own** debug keystore, which does **not** match the phone's installed app.
`adb install -r` then fails and the only way forward is uninstall — which destroys
`rustedwax_keys.xml` and `rustedwax_youtube_session.xml`, because both are
`EncryptedSharedPreferences` under an Android Keystore master key that is deleted with the package.
The dedup ledger and settings are plain and would survive a file-level backup; those two would not.

The desktop's `~/.android/debug.keystore` was copied to `C:\Users\rom\.android\debug.keystore` and
**matches**: cert SHA-256 `631e83b9b71de67fd4d109da43029b8078424673575cf773ccad3f88a8869d29`. Always
verify with `apksigner verify --print-certs` before installing. The laptop-generated one is parked at
`debug.keystore.laptop-generated`.
